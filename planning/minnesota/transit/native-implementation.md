# Glacier Line — native implementation handoff

This is a source-read implementation plan, **not installed train service**. No Rust, pack, station geometry, exporter or controller was changed for this audit. The current network contract is [glacier-line.json](glacier-line.json); the reviewed St. Paul room is [MnStPaulUnionDepot.json](MnStPaulUnionDepot.json). Its city exterior remains unbound. Each of the other five stops still needs its own reviewed room, conductor route, public entrance and safe arrival before a six-stop playable claim.

## Use the existing interpreter and train visual

Use thirty explicit, guarded source/destination branches, with the five other stops in the JSON line order. Each selected branch runs normal native script commands and the existing `special MagnetTrain`. It then uses **`warpfacing DESTINATION_CONSTANT, x, y, DOWN` immediately followed by `newloadmap MAPSETUP_TRAIN`**, targeting the destination's declared public Floor arrival. Do not interpolate a map name from menu text or make a frontend travel dispatcher.

This is the smallest existing path for arbitrary stops. `parse_script_map_commands` accepts explicit `warp`/`warpfacing` targets and checks constants through the supplied `BTreeMap<String,String>`; `warpcheck` has no destination argument and resolves the live warp under the player. A single fixed train-door warp cannot choose five destinations. `warpmod` changes the shared backup-warp tuple (`backup_warp_map_name` / `backup_warp_index`), rather than rewriting a normal door's fixed target; it adds unnecessary backup-warp state and target-index coupling here. See [script parsing](../../../crates/crystal-assets/src/script_parsing.rs:701), [map-command application](../../../crates/crystal-assets/src/game_data_scripts.rs:3334) and [warpmod semantics](../../../crates/crystal-core/src/systems/script_runtime.rs:1028).

The controller already stages a following `newloadmap` before committing **any** pending script warp: [execute_visible_pending_script_warp](../../../crates/crystal-bevy/src/bevy_shell/battle_results.rs:5356). [take_visible_pending_map_load](../../../crates/crystal-bevy/src/bevy_shell/credits.rs:4483) commits that staged warp, retains the source cursor and defers the destination scene until the source continuation ends. [Pending-request settling](../../../crates/crystal-bevy/src/bevy_shell/deterministic_session_settling.rs:5170) prioritizes `newloadmap`. The actual map transition uses existing [transition_pending_script_warp](../../../crates/crystal-assets/src/game_data_scripts.rs:3471), including object setup, map callbacks, music and snapshot commit. That function currently executes the same warp callback family for the physical transition; `MAPSETUP_TRAIN` and `MAPSETUP_WARP` have the same callback list in [script_warps.rs](../../../crates/crystal-core/src/systems/script_warps.rs:195).

The existing [two-station native regression](../../../crates/crystal-bevy/src/bevy_shell/tests/audio_and_battle_ui.rs:393) proves `warpcheck` → `newloadmap MAPSETUP_TRAIN`, retained PLAYER movement, the real 120-frame `wait 20`, destination scene ordering and rejection of a departure NPC command in the arrival map. The adjacent train-direction test proves settling both animation directions. The proposed explicit `warpfacing` + train-load combination still needs its own production-input regression; these source reads do not make it a passing six-stop ride.

`MagnetTrain` reads the current script accumulator, accepting only `TRUE`/`1` or `FALSE`/`0`. It does **not** choose a station. [The visual adapter](../../../crates/crystal-bevy/src/bevy_shell/battle_results.rs:2821) maps 1 to visual direction −1, and 0 to +1. Authoring convention: destination index less than origin index uses `setval TRUE` (toward Detroit Lakes); greater uses `setval FALSE` (toward Winona). No new graphics special or audio is required. Retain the supplied pack's train art/music/SFX.

## Menu, guards and cancellation

The current menu model has static `options: Vec<String>` and no per-option enabled flag or event-dependent label: [ScriptVerticalMenuDefinition](../../../crates/crystal-assets/src/map_modules.rs:79). [vertical_menu_options](../../../crates/crystal-assets/src/script_parsing.rs:1166) reads literal quoted `db` strings. [open_vertical_menu](../../../crates/crystal-assets/src/game_data_scripts.rs:6478) clones those options; selection validates the exact row and writes a **one-based** accumulator value. Do not claim native grayed-out or dynamically disabled rows already exist.

A leaf-only implementation can satisfy the current visible-unavailability contract using **32 authored menu variants per station**, selected by a five-flag `checkevent`/`iftrue` decision tree. This is a bounded lowering of the six-stop network contract into supported scripts, not a terrain generator or another command catalog. Each variant has five fixed destination rows in line order, followed by CANCEL. Mark each unvisited row with ` X` and explain `X = NOT VISITED` in native dialogue. Keep the same row-to-station mapping across every variant; do not remove locked rows and accidentally change indices. Even the longest label, `DETROIT LAKES X`, fits 18 columns. Use ordinary `MENU_BACKUP_TILES`, a fitting menu rectangle, `dw` to the data label, default row 1, `STATICMENU_CURSOR`, count 6 and six quoted `db` strings. Do not set `STATICMENU_DISABLE_B`. Inspect the six-row menu at 160×144 before accepting its layout. If truly disabled/grayed rows are required later, that is a real shared menu-model/controller feature, not expressible by existing static menu metadata.

The normal conductor flow is:

1. `faceplayer`, `opentext`, `checkevent EVENT_MN_COURIER_DEFEATED`; deny without moving if false. With no visited destinations, give a clear refusal and end; do not open a useless boarding sequence.
2. Determine the five visited bits through native checks; jump to one variant containing `loadmenu`, `verticalmenu`, `closewindow`. These commands must remain together in the same script body: `parse_script_vertical_menus` associates a menu with the preceding load in that body, not across an arbitrary `scall`/jump.
3. Immediately dispatch the selected result with `ifequal 1..5` to **fixed destination labels**. Both B and the sixth CANCEL row reach the no-travel cleanup. Do not check flags between selection and row dispatch: `checkevent` overwrites the same accumulator.
4. Inside the chosen destination label, recheck service activation and that destination's exact visited event before any conductor/player movement or animation. A visibly marked row is not authorization. Stale or locked choices take ordinary denial text and return control.
5. Present the boarding text through the normal text owner, close it, then run only the selected station's checked boarding/reset movements. Set the animation direction only after all event checks; `setval` deliberately replaces the selection value.

B cancellation is already supported: [press_visible_b_button](../../../crates/crystal-bevy/src/bevy_shell/deterministic_session_settling.rs:1901) calls [close_active_runtime_surface](../../../crates/crystal-bevy/src/bevy_shell/credits.rs:4134), which writes accumulator **0**, closes the menu and resumes the retained script. The explicit CANCEL row returns 6. Neither should move objects, modify flags, money, party, backup warp state or map. Finish with `closetext` and `end`; verify the following movement and Start inputs through `VisibleShellController::press`. A menu cursor or closed textbox alone is insufficient proof.

## St. Paul boarding and destination arrival

The frozen St. Paul source has conductor (17,9), sole public boarding approach (17,10), platform (17,7), train doors (12,5)/(17,5), protected ride arrival **(17,11)** and separate city-door arrival (15,21). The conductor plus native fence closes the throat. These coordinates are core walking tiles; never double them when emitting script arguments.

For a successful departure, the planned existing `applymovement` sequence is:

- Conductor: UP, UP, RIGHT, RIGHT, `step_end` → (19,7).
- PLAYER, starting at (17,10): UP ×3, LEFT ×5, UP ×2, `step_end` → (12,5).
- **Before map load**, conductor: LEFT ×2, DOWN ×2, `step_end` → original (17,9), facing DOWN. The player is already out of the way. The normal movement commands are `step` with an uppercase direction argument, not invented `step_up` command names.
- `setval TRUE/FALSE`; `special MagnetTrain`; selected explicit `warpfacing` and immediately `newloadmap MAPSETUP_TRAIN`.
- Retained continuation may use only PLAYER turning/movement, `wait` and `end`. For an arrival already at the public Floor, a PLAYER `turn_head DOWN`, `step_end` movement is sufficient; no forced platform exit or destination conductor movement is necessary.

The source-owned movement program can move **PLAYER** after a map load. Named departure objects cannot: [apply_script_movement](../../../crates/crystal-assets/src/game_data_scripts.rs:3983) explicitly permits the live PLAYER while requiring named objects to belong to the current map. Consequently restore the source conductor before loading, construct the destination conductor at its own home anchor, and let the source stream end before destination scenes. Do not append a destination-conductor command to the departure script. Do not add variable/flag/map commands after the transition merely because PLAYER movement works: several command adapters require the source map to equal the current map. Avoiding those commands removes an unnecessary continuation hazard.

Every other station needs its own measured approach/boarding/reset program and public arrival; do not copy St. Paul's coordinates into dissimilar rooms. Arrivals must be native FLOOR, outside all actor bodies, south of the protected throat and outside every active carpet/train-door/coordinate trigger. Do not target either train door on arrival. Bind the four St. Paul city carpets (14..17,23) to the one actual future city's passive return, with separate indoor safe Floor arrival/return records. That binding cannot be completed until the actual St. Paul facade exists. The source train doors serve the scripted boarding boundary; they must never become unguarded public transport or a fixed wrong-destination warp. Run the native topology validator against the chosen explicit-command representation before adding any static train-door event solely to appease a graph check; no checker should be relaxed.

## First visits and Q03 authority

Each station gets a native `MAPCALLBACK_NEWMAP` callback containing only `setevent <its-own-visited-event>` and `endcallback`. Emit the callback in `module.map_script_section_commands`, following `def_callbacks`, and preserve it in the raw map-script section when installing the module. `authoring::finish` supplies empty scene/callback sections only when the section is empty; it does not invent a visit callback. [apply_map_setup_callbacks](../../../crates/crystal-assets/src/game_data_overworld_and_saves.rs:215) reads those typed callback declarations; [execute_map_callback_script_body](../../../crates/crystal-assets/src/game_data_overworld_and_saves.rs:307) supports the flag commands and native branches. Do not launch dialogue or a menu in this small visit callback.

NEWMAP runs for real door/train entries; it does not intrinsically distinguish a foot entry from a ride. The invariant comes from geometry plus authorization: public initial entry is through the city/outpost door; an unvisited station cannot be a ride destination; therefore a permitted train callback can only re-set an already true visited event. Passing intermediate stops loads no map and sets no flags. No station Fly target or other bypass should be added. Explicit fixture placement is setup, not proof of physically earned visits. `MAPSETUP_CONTINUE` excludes NEWMAP; saved event flags remain authoritative after Continue rather than granting a fresh visit during load.

Allocate six unique EVENT identifiers additively in `pack.data.story_event_script_constants.global`, preserving existing numbers and checking EVENT numeric collisions/overflow, following [allocate_events](../../../crates/crystal-assets/src/boundary_basecamp_story.rs:291). Do not add them to initial earned flags. The courier service flag must only be set by the courier's successful native post-battle continuation, never a timetable, callback or conversation shortcut.

There is a **source-binding conflict to resolve before implementation**: [actors.json](../actors.json) reserves `MN_CITY_COURIER` at `MnStPaul` (31,23), requiring `BADGE_3` and `EVENT_MN_DISPATCH_NOTE`. The depot currently has placeholder `MN_ST_PAUL_DEPOT_COURIER` at (20,16). Bind one canonical Q03 encounter to the reviewed depot and update the shared story/actor reservation deliberately; do not install two independently rewarding couriers. [story.json](../story.json) specifies `MN_LODE_COURIER`, Magnemite23 / Drowzee22, victory event `EVENT_MN_COURIER_DEFEATED`. Preserve the upstream prerequisites unless the integration owner explicitly revises that story contract. Use the existing boss sequence (`loadtrainer`, `startbattle`, `reloadmapafterbattle`, then victory flag) and actual loss/whiteout semantics, as the [Q07 story binder](../../../crates/crystal-assets/src/boundary_basecamp_story.rs:93) does. No Q06 depot, gym, lighthouse, survey or Safari flag is granted by train service.

| --- | --- |

| Flag/control/text tables; raw object/warp/BG sections | `authoring::finish(&pack, &mut module)`; it calls `parse_script_flag_commands`, `parse_script_control_commands`, `parse_script_text_commands`, `parse_script_text_bodies` and existing item/economy/scene parsers |

Build on a clone and publish atomically only after validation: preserve all existing source/native maps, tables, audio, runtime files, HOME/recovery and unrelated manifests; add only new station maps, explicit story/event/trainer additions and the manifest/identity changes required by that overlay. ## First implementation slice and proof boundary

Start with a prepared station/service binder accepting six real authored `MapModule`s and six validated typed anchor contracts, not a frontend destination callback. It should reject absent/duplicate stop ids/constants/visited flags, changed source rows, unbound city exits, unreachable approaches, non-Floor/trigger-overlapping arrivals, missing movement labels and a conductor throat that can be walked around. A partial two-station fixture may prove the transport machinery using explicitly labeled existing rooms; it cannot stand in for six published Minnesota stations or an earned Q03 journey.

Before calling the network playable, Root's warm test/publication work must establish:

- Asset/core: all 30 directed bindings resolve to the correct station, native Floor coordinate and facing; all 32 menu variants retain the correct five-row order and unavailable marking. Reject wrong visited flags, wrong map constants/arrivals, stripped courier checks, broken reset movements and mismatched typed/raw script tables. Preserve old content/audio exactly, verify actual CBOR write/read.
- Production controller: walk public city/outpost entrances to earn all visit flags. Deny before Q03, with zero destinations and at each locked destination branch even when a stale choice is supplied. Prove A/page ownership, B/explicit CANCEL cleanup, no money/party/progression changes on refusals and no walking around the conductor.
- Real rides: one selected lower-index and one higher-index trip through `VisibleShellController::press`, native animation/audio arrival, authoritative destination map/position/facing, source conductor restored before leaving, destination conductor still blocking, input returned and repeat departures possible. Test all 30 bindings at the script/core layer plus production ride coverage; expand controller pairs if any station has a distinct movement risk.
- Q03: actual selected move spends PP, win grants the courier event only after victory, defeat does not, repeat conversation does not rematch/reward; the earned flag activates train service. Initial legal-party/badge/upstream-note setup must be labeled.
- Persistence: after actual arrival, open production Start, Save, then `VisibleShellController::load_save` / Continue; verify station/position, visited+service flags, party/PP, money and ordinary movement. [The public boundary](../../../crates/crystal-bevy/src/bevy_shell.rs:607) supplies `press`, `wait_frames`, `save` and `load_save`. Do not replace a journey with post-setup location/state writes. Mid-animation save/resume is not established by the arrival-only contract.
- Retain every full-resolution source/native/train capture, raw RGBA scene, conversion/crop/preview and rejected pass with the existing archival helpers; inspect handheld framing and actual input. No new train run or screenshot was produced for this source-only handoff.

No missing six-destination dispatcher was found: explicit guarded map commands use existing production boundaries. The concrete remaining work is native station/entrance authoring, source-consistent Q03 binding, static menu variant lowering, table population and fresh controller proofs. Dynamic disabled rows and an unguarded arbitrary-destination `warpcheck` are not existing capabilities and should not be assumed.
